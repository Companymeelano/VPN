# FIX-PLAN — سه مشکلی که گزارش دادی

> این سند پاسخ مستقیم سه نکته‌ی توست. «کد اپ» در این ریپازیتوری نبود (فقط `README.md`)،
> پس اینجا دو چیز هست: (۱) تشخیص مبتنی بر نشانه‌ها + کاری که من به‌عنوان زیرساخت/کد مرجع ساختم،
> (۲) چک‌لیست دقیق برای اعمال روی سورس خودت.

---

## ۱) «چند ثانیه بعد از اتصال، کل گوشی هنگ می‌کند»

نشانه‌ای که دادی مهم‌ترین سرنخ است: **فقط در همان بخش**، و **چند ثانیه بعد خودبه‌خود درست می‌شود**.
این الگو تقریباً همیشه یکی از این چهار علت است — و هر چهارتا در مسیر اتصال یک اپ VPN دیده می‌شوند:

| # | علت | چرا دقیقاً همین رفتار را می‌دهد | درمان (در همین ریپو پیاده شد) |
|---|---|---|---|
| 1 | کار سنگین داخل ترد اصلی سرویس: `VpnService.onStartCommand` → resolve DNS سرور، `InitConfig/StartVpn` هسته، ساخت JSON پروفایل | ترد اصلیِ پروسه‌ی اپ همان تردی است که UI روی آن است؛ چند ثانیه قفل = هنگ کامل | `VpnOrchestrator` همه‌چیز را روی `Dispatchers.Default/IO` می‌برد؛ `onStartCommand` فقط صف می‌کند و برمی‌گردد |
| 2 | **آبارش نوتیفیکیشن**: هر read/write روی fd تونل → `notify()` | `notify()` یک فراخوانی binder به `system_server` است؛ با چندصد فراخوانی در ثانیه، *سیستم‌عامل* مکث می‌کند، نه فقط اپ. این تنها علتی است که «کل گوشی» را کند می‌کند | در `MeelanoVpnService` نرخ نوتیفیکیشن به ۱Hz و فقط «در صورت تغییر معنادار متن» محدود شده (`movedEnough`) |
| 3 | مسیر/DNS قبل از بالا آمدن تونل: `addRoute(0.0.0.0,0)` + `addDnsServer(...)` وقتی هنوز پروکسی handshake نشده | lookup تمام اپ‌های دیگر معلق می‌ماند تا timeout (≈۵s) → کاربر «هنگی» را در کل گوشی حس می‌کند | ترتیب در `VpnOrchestrator`: پروفایل → resolve → استارت هسته → `establish()` → **بعد از آن** DNS/قاعده‌گذاری + host-route برای IP سرور |
| 4 | پارس لیست پروکسی/`SharedPreferences.commit()` در لحظه‌ی اتصال | لیست‌های رایگان مگابایتی‌اند؛ Gson/JSON روی ترد اصلی = ۰٫۵ تا ۳ ثانیه جامد | کار سنگین به **سرور** منتقل شد: اپ فقط `vip.json` (چند کیلوبایت، با ETag) را می‌خواند. `Prefs` هم با `apply()` نوشته می‌شود |

### چطور قطعی تأییدش کنیم (۲۰ دقیقه، بدون حدس)
```bash
adb logcat -b events | grep -E "am_anr|am_kill|wm_pause"      # ANR واقعی یا نه
adb shell dumpsys gfxinfo <pkg> framestats                     # JankSpec؛ «Skipped 40 frames» = ترد اصلی
adb shell am trace_gfx <pkg>                                    # یا Perfetto capture
./gradlew assembleRelease && adb install -r app-release.apk    # همیشه release profile را بسنج، نه debug
```
اگر در Perfetto یک بلوک `StrictMode`/`Davey!` روی `main` دیدی، همان مورد ۱ است. اگر ترد اصلی آزاد بود
ولی کل سیستم کند بود، مورد ۲ یا ۳ است.

### نشانه‌های جانبی که با تشخیص من جور درمی‌آید
- «بعد از چند ثانیه درست می‌شود» = timeout یک کار همگام (DNS یا handshake)، نه کرش.
- بخش تست/دریافت پروکسی کند است = همان ۴، چون در همان لحظه اتفاق می‌افتد.

## ۲) «پروکسی‌های رایگان درست اعمال نمی‌شوند»

سه ترفیعِ ساختاری که انجام شد:

1. **اعمال = restartِ درست، نه نوشتن در pref.** `ServerFeedRepository.applyNode()` ترتیب را رعایت
   می‌کند: ذخیره‌ی id → `MeelanoVpnService.start(node)` → و بعد از آن، UI وضعیت را **از سرویس**
   می‌خواند (`MeelanoVpnService.phase`)، نه از «لمس کاربر». تا وقتی این یکی‌شدن منبع حقیقت انجام
   نشود، «اعمال شد» فقط توهم است.
2. **نرمال‌سازی روی سرور.** هر فرمتی (`vless://`, `vmess://`، `ss://` هر دو سبک SIP002 و legacy،
   `trojan://`, `hy2://`، خطوط `ip:port`، اشتراک base64، حتی HTML) به یک آبجکت ثابت تبدیل می‌شود
   و `raw` بازسازی‌شده به اپ می‌رسد. ۹۰٪ «اعمال نمی‌شود»ها از یک فیلد جاافتاده (`security/flow/sni/host/path/pbk/sid`)
   یا `port` رشته‌ای می‌آید؛ آن فیلدها حالا اجباری و تست‌شده‌اند (۶۵ تست در `backend/v/tests/run.php`).
3. **فقط نودِ جان‌دار وارد لیست می‌شود.** خط لوله‌ی سرور: fetch → dedupe → پالایش پورت/IP خصوصی →
   پروب TCP → گیت «اتصال به Google/Cloudflare» → امتیاز → انتشار. چیزی که به دست کاربر می‌رسد
   از قبل ردِ فیلتر شده است، پس «انتخاب می‌کنم و کار نمی‌کند» به «لیست کوتاه‌تر ولی کارا» تبدیل می‌شود.

## ۳) «بخش تست سخت‌گیرانه است»

بله — و راه‌حل دو تکه است، چون تستِ سمت اپ و تستِ سمت سرور دو چیز متفاوت‌اند:

- **تست نباید گیتِ مسیر اتصال باشد.** در طرح جدید، اتصال وصل می‌شود و ارزیابی در بک‌گراند
  انجام می‌شود (`در حال ارزیابی…`). هیچ‌وقت «اول تست، بعد اجازه‌ی استفاده» نه.
- **سنجش لایه‌لایه، نه ICMP.** `Probe::tcp` (پورت باز است؟) ≠ `gate` (آیا واقعاً ترافیک TLS را
  پروکسی می‌کند؟) ≠ بازخورد کاربر (آیا از داخل ایران مفید است؟). `ping` معمولاً بلاک است؛ با آن
  «مرده» اعلام کردن، پروکسی سالم را می‌کشد.
- **آستانه‌ی منصفانه + رتبه به‌جای صفر و صد:** `A/B/C/D` بر اساس `p50 latency` و
  `reliability` (فرمول: `(ok+1)/(ok+fail+2)`). یک نود تازه هرگز A نمی‌گیرد چون نمونه ندارد — ولی
  حذف هم نمی‌شود؛ فقط B است. (این را در تست‌ها قفل کرده‌ام: *a fresh node with no samples cannot earn an A*.)
- **VIP هرگز به‌خاطر یک پروب ناموفق حذف نمی‌شود** (`vip.dropIfProbeFails=false`)؛ برای لیست رایگان
  حذف می‌شود. یک تست برای همین وجود دارد.
- **حافظه‌ی بدنامی:** سه شکست متوالی → ۶ ساعت خنک‌سازی (`Ledger`)؛ گزارش‌های کاربر هم با آستانه‌ی
  بالاتر (۶ برابر `trustFloor`) می‌توانند نودی را بن کنند. بعد از مهلت، شانس بازگشت دارد.

## ۴) چیزهایی که خودت خواستی و در این ریپو ساخته شد

| خواسته | چیزی که ساخته شد |
|---|---|
| کنترل اتصال جذاب/سه‌بعدی در بالای گوشی + سرعت + قطع/وصل | `android/app/src/main/java/ir/meelano/vpn/ui/VpnControlPanel.kt` (حلقه‌ی اتصال با bezel/well/sheen + سرعت زنده) و `android/app/src/main/java/ir/meelano/vpn/qs/MeelanoTileService.kt` (کاشی Quick Settings: همان کنترل بالای گوشی، بدون باز کردن اپ) |
| اپ که بسته می‌شود، همه‌چیز بسته می‌شود | سرویس foreground با `START_STICKY`، `stopWithTask="false"`، `onTaskRemoved` که تونل را نمی‌کشد، `BootReceiver` + Watchdog و (اختیاری) `android:process=":vpn"` — همه در `android/app/src/main/AndroidManifest.xml` |
| لیست VIP از هاست اشتراکی (`/v`) با ماسک‌کردن نام‌ها و فقط «Vip Meelano» + پرچم | `backend/v/` با اکشن `?action=vip`؛ نام فروشنده **هرگز** در پاسخ نیست (تست: *no vendor remark anywhere in the payload*)، vmess هم با `ps` بازنویسی می‌شود؛ `cc` دو‌حرفی برای پرچم خودِ اپ |
| دریافت سریع‌تر + پروکسی‌های ماندگار + عبور از تست، در لیستی شبیه VIP | `?action=free` با خط لوله‌ی aggregation از منابع انتخاب‌شده (`sources.php`)، پروب/رتبه‌بندی سمت سرور، کش + ETag؛ خروجی دقیقاً همان schema لیست VIP (تست: *same required contract as vip*) |
| فایل بروزرسانی نسخه روی همان هاست + نصب خودکار | `?action=version` + آپلود APK از پنل + `version.json` امضاشده (HMAC + sha256) + `UpdateManager.kt` که دانلود/وریفای/نصب را انجام می‌دهد. صادقانه: «نصب بی‌صدا» روی اندروید بدون Device Owner ممکن نیست — چیزی که می‌شود «دانلود خودکار + یک لمس برای تأیید» است |
| فقط هاست اشتراکی، بدون Node و بدون SSH | کل بک‌اند PHP خالص است: بدون composer، بدون exec، بدون daemon. کش روی فایل، قفل با `flock`، بیلد تنبل (lazy) + اختیاری cron در cPanel |

**باقی‌مانده‌ی کار:** اتصال این کدها به سورس واقعی اپ. تا آن کد را نگذاری، هیچ‌کدام از موارد بالا
روی دستگاه تو اجرا نشده است — من فقط سمت سرور را واقعاً اجرا و تست کردم (اینجا اندروید SDK نداریم).
